# 05. 대사·반응 시스템 — LLM 없이 방대한 반응성을 만드는 법

> 질문: "내 선택에 따라 달라지는 대사를 전부 쓰려면 스크립트가 무한히 필요하지 않나?"
> 답: **전부를 쓰지 않는다.** 대사를 '분기 트리'가 아니라 **'조건이 붙은 문장 데이터베이스'** 로 만들고,
> 엔진이 매 순간 **가장 구체적으로 맞는 문장**을 골라 쓴다. 문장 자체는 개발 단계에서 LLM으로 대량 생산하고 사람이 다듬는다.
> → **런타임 LLM 없이도** 플레이어는 "세상이 나를 기억한다"고 느낀다.

---

## 1. 왜 분기 트리로는 안 되는가

```
선택 3개 × 10번 = 3^10 = 59,049개의 경로   ← 전부 쓰는 건 불가능
```

전통적인 분기 대화는 선택이 늘어날수록 지수적으로 폭발한다. 대신 업계의 검증된 방법을 섞는다.

| 기법 | 대표 사례 | 핵심 |
|------|-----------|------|
| **규칙 기반 동적 대사** | Valve *Left 4 Dead* (GDC 2012 "AI-driven Dynamic Dialog") | 상황을 '질의'로 만들고, 조건이 가장 많이 맞는 대사를 선택 |
| **우선순위 반응 대사** | Supergiant *Hades* (수만 줄) | 이벤트·관계·진행도 조건으로 수천 개 대사 중 가장 적절한 것 출력 |
| **스토리렛 + 상태(Quality)** | Failbetter *Fallen London* | 거대 트리 대신 상태로 연결되는 작은 조각 |
| **템플릿 + 변수 치환** | *Crusader Kings*, *Wildermyth* | 한 문장 틀로 수백 가지 인물·관계 조합 표현 |
| **문법 기반 생성** | *Caves of Qud* | 묘사·소문·역사 문장을 문법 규칙으로 조합 |
| **분기 후 수렴 + 흔적 남기기** | 대부분의 상업 RPG | 큰 줄기는 합쳐지되, 작은 대사들이 과거 선택을 "기억"한다 |

> 핵심 통찰: 플레이어가 느끼는 반응성의 대부분은 **큰 분기가 아니라 작은 '알아봐 주는 한마디'** 에서 온다.
> "지난번에 내 빵을 훔쳤지" 한 줄이 30분짜리 분기 퀘스트보다 세상을 살아있게 만든다.

## 2. 대사 데이터베이스 구조

### 2.1 질의(Query) — 엔진이 대사가 필요할 때 만드는 것

```yaml
query:
  concept: 인사                 # 무슨 상황의 대사인가 (§3 개념 목록)
  speaker: npc_bram             # 말하는 사람
  speaker.role: 배급막사관리인
  speaker.race: 인간
  speaker.archetype: 무뚝뚝한보호자
  speaker.mood: 불안
  listener: player
  rel.trust: 45                 # 화자 → 플레이어 관계
  rel.affection: 30
  memory: [player_hid_refugees, player_paid_debt]   # 화자가 기억하는 플레이어 행동
  world.season: 겨울
  world.clock.northern_exodus: 3
  place: 절름발이_수탉
  time: 밤
  player.visible: [성표:순종의빛, 피묻음]           # 화자 눈에 보이는 것
  player.condition: [부상:중상]
```

### 2.2 대사 규칙(Rule) — 미리 써둔 문장 + 조건

```yaml
- id: bram_greet_bloody_night
  concept: 인사
  speaker: npc_bram
  criteria:
    - player.visible has 피묻음
    - time == 밤
    - rel.trust >= 30
  lines:
    - "문 닫아. 빨리. …누구 피야, 그거."
    - "또 무슨 짓을 하고 온 거냐. 아니, 말하지 마. 지하로 내려가."
  then: { set_flag: bram_saw_blood, offer_scene: bram_hide_player }
  weight: 10
  cooldown: 3일

- id: role_rationer_greet_generic
  concept: 인사
  speaker.role: 배급막사관리인
  lines:
    - "배급은 해 뜰 때다. 그 전엔 없어."
    - "줄 서."

- id: generic_human_greet_tired
  concept: 인사
  speaker.race: 인간
  world.season: 겨울
  lines:
    - "{weather_short}. 살아는 있구먼."
```

### 2.3 선택 알고리즘

```
1. concept가 같은 규칙만 후보로
2. 모든 criteria를 만족하는 규칙만 남김
3. 점수 = 만족한 criteria 수 (구체성) + 고유 화자 보너스(+5)
4. 가장 높은 점수 그룹에서 weight 비례 무작위 선택
5. 최근 사용·cooldown 중인 규칙 제외 (반복 방지)
6. lines 중 하나 선택 → 변수 치환 → 조사 보정 → 출력
7. then: 효과 실행 (플래그, 장면 제안, 관계 변화)
```

**4단계 폴백(fallback) 계층** — 어떤 상황에서도 반드시 무언가를 말한다:

```
① 고유 NPC 전용 + 상황 특화    (가장 구체적, 가장 적게 씀)   예: 브람이 피 묻은 플레이어를 밤에 볼 때
② 역할(직업) 전용               예: 배급 관리인이 하는 인사
③ 종족 × 성격 원형              예: 무뚝뚝한 인간이 하는 인사
④ 범용                         예: 아무나 하는 인사
```

> 중요한 NPC의 중요한 순간만 ①로 쓰고, 나머지는 ②~④가 메운다.
> 콘텐츠가 늘어날수록 ①이 늘어나며 세계가 점점 더 정교해진다 — **점진적 업데이트에 최적.**

## 4. "내 선택에 따른 결과 대사"를 만드는 4가지 장치

### 4.1 기억(Memory) 태그
NPC는 플레이어의 행동을 **기억 태그**로 저장한다 (이벤트 로그에서 자동 생성, 시간이 지나면 희미해짐).

```
player_stole_from_me (강도 3, 412일 전)
player_saved_my_child (강도 5, 영구)
player_lied_to_me_caught (강도 2, 30일 전)
```

→ 모든 대사 규칙이 `memory has ...` 조건을 쓸 수 있다.

### 4.2 같은 NPC, 다른 과거 → 다른 대사 (예시)

**장면**: 3개월 후, 플레이어가 다시 배급 막사에 들어온다. 화자: 브람.

| 플레이어의 과거 행동 | 브람의 첫마디 |
|----------------------|---------------|
| 탈주자 가족을 함께 숨겨줌 | "…왔냐. 지하 애들이 너 안부 묻더라. 앉아. 오늘은 내가 산다." |
| 탈주자를 목줄단에 밀고함 | (잔을 닦던 손을 멈춘다) "배급은 끝났다. 나가." |
| 브람의 배급품을 훔침 (들킴) | "또 왔어? 이번엔 내 눈앞에서 가져가 보지 그래." |
| 브람의 배급품을 훔침 (안 들킴) | "요즘 창고 쥐가 많아. 혹시 본 거 없냐?" *(의심하는 눈)* |
| 아무 관계 없음 | "줄 서." |
| 피의 원형장에서 30승을 거두고 돌아옴 (소문 도달) | "…네가 그 '회색여울의 송곳니'라고? 웃기지 마. 그 비실거리던 놈이?" |

> 이 6줄은 6개의 짧은 규칙일 뿐이다. 분기 트리는 하나도 없다.

### 4.3 템플릿 + 변수 (조합 폭발을 우리 편으로)

```
"{target.name}{target.이가} {event.place}에서 {event.verb_past}다더군. {speaker.opinion_phrase}"
```
→ 소문 시스템의 수천 가지 사실(Fact)을 **하나의 틀**로 말할 수 있다.
- `opinion_phrase`는 화자의 성향·관계에 따라: "잘됐지 뭐." / "어리석은 짓이야." / "…신이시여."

### 4.4 분기 후 수렴 + 상태 흔적
큰 사건(봉기 성공/실패)만 진짜로 분기하고, 나머지는 **상태값**만 바꾼 뒤 같은 흐름으로 합쳐진다.
대신 그 상태값이 이후 수백 개의 작은 대사·스토리렛 조건으로 계속 쓰인다.

## 5. 한국어 특화 처리

### 5.1 조사 자동 보정
변수 치환 후 받침에 따라 조사를 자동 선택한다.

| 표기 | 받침 있음 | 받침 없음 | 예 |
|------|-----------|-----------|----|
| `{x.이가}` | 이 | 가 | 브람**이** / 사라**가** |
| `{x.은는}` | 은 | 는 | |
| `{x.을를}` | 을 | 를 | |
| `{x.과와}` | 과 | 와 | |
| `{x.으로로}` | 으로 | 로 (ㄹ받침도 '로') | 회색여울**로** / 성채**로** |
| `{x.아야}` | 아 | 야 | 페인**아** / 사라**야** |

```ts
// 한글 음절의 받침 여부: (code - 0xAC00) % 28 !== 0
```

### 5.2 경어 체계 = 신분 체계 (그림다크 세계의 핵심 표현 장치)

| 화자 → 청자 | 말투 | 예 |
|-------------|------|----|
| 인간 → 용인·용족 | 극존칭 + 자기비하 | "나리, 이 비천한 것이 감히…" |
| 용인 → 인간 | 하대 반말, 이름 대신 '노예', '무혈자' | "무혈자. 고개 들지 마라." |
| 용족 → 모두 | 고어체 하오체, 경멸 | "작은 것이 감히 말을 하는가." |
| 엘다르 → 인간 | 다정한 반말 (애완동물에게 말하듯) — 더 섬뜩함 | "착하지. 오늘은 노래를 불러 보렴." |
| 두르강 → 인간 | 사무적 하게체 | "계약서에 손도장 찍게." |
| 인간 ↔ 인간 | 반말/해요체, 노예말 은어 | "야, 감독관 온다. 고개 숙여." |
| 그롬 → 투사 | 짧은 명령형, 거친 말 | "싸워. 이기면 먹는다." |

- 대사 규칙에는 원문을 **중립 의미**로 쓰지 않고 말투별로 직접 쓴다 (자동 경어 변환은 어색해지기 쉬움).
- 대신 **말투 프로파일**을 NPC에 붙여 LLM 생성 단계에서 일관된 말투를 유지한다 (§7).

### 5.3 말투 프로파일 예

```yaml
speech_profile:
  npc_bram:   { 기본: 반말, 문장길이: 짧음, 말버릇: ["…", "됐고"], 금지어: [감탄사 과다], 사투리: 북부억양 약간 }
  npc_godric: { 기본: 하대, 상위자앞: 아첨조, 말버릇: ["흠", "빚이란 말이다"], 특징: 돈 이야기로 귀결 }
  npc_elsa:   { 기본: 반말 노인체, 말버릇: ["얘야"], 특징: 약초 비유, 수수께끼 같은 말 }
```

## 6. 필요한 분량 추정

| 층 | 계산 | 문장 수 |
|----|------|---------|
| ④ 범용 | 70 개념 × 4 변형 | 280 |
| ③ 종족 × 성격 원형 | 70 개념 × (15 종족·말투) × (12 원형 중 관련 4) × 2 | 약 8,400 |
| ② 역할(직업) | 45 직업 × 30 개념 × 3 | 약 4,000 |
| ① 고유 NPC | 수직 슬라이스 22명 × 150 + 이후 90명 × 80 | 3,300 → 약 10,500 |
| 기억 반응 | 50 기억 태그 × 12 원형 × 3 | 1,800 |
| 소문 템플릿 | 사실 유형 120 × 3 | 360 |
| 묘사 문법 조각 | 날씨·장소·감정·전투 | 약 6,000 |
| 스토리렛 | 1.0 기준 5,000개 × 평균 600자 | (300만 자) |
| **합계** | | **대사 약 3만 줄 + 스토리렛 300만 자** |

> 소설 수십 권 분량이다. 사람 혼자 쓰면 수년, **LLM 파이프라인 + 사람 검수**면 현실적이다.
> 단, 한 번에 다 만들 필요는 없다. 수직 슬라이스(회색여울)는 대사 약 6,000줄 + 스토리렛 150개면 충분하다.

## 7. 개발 단계 콘텐츠 생성 파이프라인 (LLM은 "작가실"에서만)

```
① 명세서                    ② 생성                 ③ 자동 검증              ④ 사람 검수        ⑤ 커밋
세계관 발췌 +              LLM이 YAML로     →    스키마·용어·조사·      →  핵심 100%      →  content/
NPC 시트 + 말투 프로파일 +   대량 생성             길이·중복·금칙어 검사       범용 10~20%
개념 목록 + 예시 10개                              + 다른 LLM의 톤 채점        샘플링
```

### 7.1 모델 선택 — 제안하신 방향이 맞다

| 콘텐츠 | 추천 모델 | 이유 |
|--------|-----------|------|
| ④ 범용 · ③ 원형 · 묘사 문법 (대량, 짧음) | **Claude Haiku 4.5** 또는 **Claude Sonnet 5.5 (effort: low)** | 짧고 반복적, 양이 중요. 비용 최소 |
| ② 역할 · 기억 반응 · 소문 템플릿 | **Claude Sonnet 5.5 (effort: low~medium)** | 맥락 이해 필요, 대량 |
| ① 고유 NPC · 핵심 스토리렛 · 출신 도입부 | **Claude Opus 5.5** (또는 Sonnet 5.5 effort: high) | 캐릭터 일관성·문장 품질이 가장 중요 |
| 검수(톤·설정 위반 채점) | Sonnet 5.5 | 생성 모델과 다른 시각 |

- Haiku 4.5는 `effort` 파라미터를 지원하지 않는다 (Sonnet 5.5·Opus 5.5는 지원). Sonnet 5.5의 low는 짧은 대사 대량 생성에 적합.
- **한국어 품질은 반드시 직접 비교해 보고 결정**한다: 같은 명세로 50줄씩 생성 → 블라인드로 골라보기 → 모델 확정.

### 7.2 두 가지 생성 경로

| 경로 | 비용 | 장점 | 단점 |
|------|------|------|------|
| **A. Claude Code (Max 구독)** | 구독료 안에서 (사용 한도 있음) | 추가 비용 0, 대화하며 다듬기 쉬움, 지금 바로 가능 | 대량 자동화엔 한도·속도 제약 |
| **B. Claude API + Batch API** | 종량제 (배치 50% 할인) | 수만 줄 자동 생성, 재현 가능한 파이프라인 | API 결제 필요 |

**추천**: 수직 슬라이스(대사 6천 줄)는 **A로 충분**하다. 본격 볼륨(수만 줄)부터 B를 쓴다.

### 7.3 API로 전량 생성할 때의 비용 어림 (2026-09 공개 가격 기준, 대략치)

가정: 요청 1회 = 대사 25줄, 입력 6천 토큰(그중 5천은 캐시되는 공통 명세), 출력 2천 토큰.

| 대상 | 요청 수 | Haiku 4.5 | Sonnet 5.5 | Opus 5.5 |
|------|---------|-----------|------------|----------|
| 대사 3만 줄 | 약 1,200 | 약 $14 | 약 $28 | 약 $55 |
| 스토리렛 5,000개 (입력 8천/출력 2.5천) | 5,000 | 약 $75 | 약 $150 | 약 $300 |
| **Batch API 사용 시** | | 약 절반 | 약 절반 | 약 절반 |

> **게임 전체 텍스트를 만드는 데 수십~수백 달러 수준.** 품질 때문에 3~5번 재생성해도 감당 가능한 규모다.
> 진짜 비용은 돈이 아니라 **사람의 검수 시간**이다. 그래서 자동 검증(③)이 중요하다.
> 가격은 바뀔 수 있으니 실제 진행 시 공식 가격표로 다시 계산할 것.

### 7.4 자동 검증 항목

- YAML 스키마 통과, 필수 필드 존재
- **세계관 용어 사전** 검사: 고유명사가 정본에 있는가 (없는 지명·인물 → 반려)
- 콘텐츠 태그 부착 (`폭력:고문`, `처형`, `식인` 등 — 플랫폼별 빌드에서 선택적으로 거를 수 있게. WORLD_BIBLE §0.3의 두 선을 넘는 문장은 반려)
- 말투 프로파일 위반 (인간이 용인에게 반말 → 반려)
- 길이 범위, 중복·유사도 (같은 개념 내 문장 유사도 0.85 이상 → 하나 삭제)
- 조사 변수 누락 (`{name}가` 처럼 직접 조사를 붙인 경우 → 반려)

## 8. 런타임 LLM과의 관계

| 상황 | 런타임 LLM 없음 (기본) | 런타임 LLM 있음 (선택 기능) |
|------|------------------------|-----------------------------|
| 일반 대사 | 대사 DB에서 선택 | 동일 |
| 기억 반응 | 기억 태그 규칙 | 동일 + 드물게 맞춤 문장 |
| 자유 대화 | 주제 메뉴 (아는 주제 목록) | 자유 입력 → 주제로 변환 → DB 대사 / 또는 생성 |
| 연대기 | 템플릿 서술 | 문학적 서술 |

> 게임은 **LLM 없이 완성**되어야 하고, LLM은 "이야기꾼 모드"로 얹는 추가 기능이다.

## 9. 구현 메모

```ts
interface DialogueRule {
  id: string;
  concept: ConceptId;
  speaker?: NpcId;                 // 고유 화자
  criteria: Criterion[];           // 순수 함수로 평가
  lines: string[];                 // 변수·조사 템플릿
  weight?: number;
  cooldownHours?: number;
  then?: Effect[];
}
// 규칙 인덱스: concept → speaker/role/race 별 버킷으로 미리 분류 → 질의마다 수십 개만 검사
```

- 규칙 수가 수만 개여도 개념별·화자별 인덱스로 나누면 모바일에서도 1ms 이내.
- **커버리지 도구**: 헤드리스 시뮬레이션에서 "폴백 ④까지 떨어진 질의"를 집계 → 다음에 써야 할 대사 목록 자동 생성.
  → 콘텐츠 작업의 우선순위를 데이터가 알려준다.
